# 需求/设计文档编写与迭代

## 适用场景

- 为新功能编写需求文档和设计文档。
- 修改已有需求、设计、共同协议、状态机、字段和改造范围。
- 用户要求参考现有文档结构、复用已有文案，或按“功能 / 现状 / 改造点”整理方案。

不适用于只改代码、只需要 code review、或不需要形成文档的临时分析。

## 文档产物

默认放在：

~~~text
.local/_doc/{feature}/
├── 方案N需求文档.md
└── 方案N设计文档.md
~~~

先写需求，再写设计，评审后再编码。已有方案被替代时保留废弃文档并在新文档中标注，不直接覆盖历史方案。

新建文档时从模板开始，章节可裁不可凑：

- 需求文档：`references/requirements-template.md`
- 设计文档：`references/design-doc-template.md`

头部元信息至少包含：编号、日期、最近更新、涉及模块或项目、关联文档、状态、结论来源。需求与设计的“最近更新”必须反映本轮真实变化。

## 需求文档结构

需求文档描述用户行为、系统目标和验收边界，不展开具体类和方法。

默认章节顺序：

1. 名词约定。
2. 问题定义、目标与当前问题清单：先写业务问题，再写目标，最后列实现该目标仍需解决的问题和已有能力。
3. 端到端流程。
4. 功能需求：字段、交互、接口和业务规则写到对应 FR 内。
5. 非功能需求。
6. 边界特例与失败处理。
7. 改动范围。
8. 风险与待决事项。
9. 验收标准，始终放最后。

每条 FR 写清：触发者、触发方式、输入、处理结果、失败反馈、用户可见位置。不要用实现类名替代用户语义。

用户补充或纠正需求时：

- 先重读当前文档，再修改。
- 保持未被需求变更影响的段落原文不变。用户明确要求“复用旧方案文案”时，禁止为了统一语气整段重写。
- 改动字段或范围后，清理旧字段、旧链路、旧状态和旧待决事项，不能只在末尾追加一句“改为 X”。
- 已解决的待决事项直接删除并顺延编号，不保留删除线。
- 验收入口、按钮、任务页、失败原因、清理与权限等用户可见要求必须能被验收项覆盖。

## 设计文档结构

设计文档默认是一份覆盖完整功能的跨模块文档。各项目按模块章节展开，避免把同一套协议和状态复制到多份文档后失去一致性；只有交付边界完全独立时，才拆成多份并显式链接共享契约。

固定主骨架：

~~~text
标题与元信息
1. 设计结论
   1.1 系统边界
   1.2 总体流程
2. 公共协议与状态约定（按需）
3. {模块 A}
   3.1 功能
   3.2 现状
   3.3 改造点（具体实现）
4. {模块 B}
   4.1 功能
   4.2 现状
   4.3 改造点（具体实现）
...
N-3. 跨模块一致性与改造清单
N-2. 实施顺序
N-1. 验证计划
~~~

### 设计结论

开头先给最终方案，不按调查过程叙述。必须包含：

- 一句话说明方案如何解决用户问题。
- 编号列出关键决策和明确不做的范围。
- 系统边界表：模块、核心职责、不承担。
- 总体流程 Mermaid，区分触发路径、公共处理、持久化和结果读取。
- 流程约束：幂等、异步、权限、数据事实源、区域路由等容易误解的边界。

### 公共协议与状态约定

涉及两个以上模块时，先集中定义共享契约，再进入模块章节。按需覆盖：

- 时间、字段、枚举和取值规则。
- 状态机及终态规则。
- 业务错误码和脱敏要求。
- 幂等键、请求哈希、重试语义。
- 共享 DTO、proto、HTTP/Dubbo/gRPC 方法和兼容性。
- 任务 ID、回调关联字段和事实源。

同一字段只能有一个权威定义。模块章节引用公共协议，不重复定义另一套。

### 模块章节

每个模块必须完整包含三个二级小节：

#### N.1 功能

该模块在本方案中新增或改变的能力，以及与其他模块的边界。

#### N.2 现状

只写与本次改造直接相关的现状：

- 已有入口、调用链、接口、表、任务类型、页面或配置。
- 可复用的能力及代码位置。
- 当前缺口和为什么不能直接满足目标。

现状必须来自源码、proto、SQL、配置或页面，不凭印象写“已有”或“对齐”。

#### N.3 改造点（具体实现）

这是设计文档的主体。每个改造点应写到开发者可以直接实施的层级：

- 文件、类、函数、接口或页面组件。
- 输入输出、字段类型、默认值、范围和校验规则。
- 数据表、索引、唯一键、状态迁移和兼容策略。
- 调用链、事务边界、并发、重试、超时和失败处理。
- 需要删除或收敛的旧逻辑。
- 对用户不可见但影响排障的日志、指标和错误信息。

按功能域继续拆成 `N.3.1`、`N.3.2` 等章节。不要使用“总体方案”“详细设计”“改动清单”等泛化标题承载大量不相干内容。

### 跨模块一致性与改造清单

必须收口：

- 端到端调用树，至少覆盖创建、执行、回调和查询路径。
- 并发与时序约束，例如先落库再下发、终态不可回退、重复回调幂等。
- 改造范围表：仓库、改动、状态。
- 本地源码可用性、共享制品版本、proto 子模块、依赖方数量。
- 不能改动但会影响边界的项目，明确写“无改动”及原因。
- 当前工作区已有原型是否保留、收敛或删除。

改动范围表不增加“仓库位置”列，本地可用性以表下脚注说明。

### 实施顺序与验证

实施顺序说明发布依赖和滚动升级约束。验证计划分开写：

- 单元测试：按模块列关键分支、边界和非法输入。
- 集成测试：按真实时序串起创建、异步执行、回调、查询和下载。
- 端到端验收：使用表格把用户目标、系统约束和设计落点对应起来。

未执行的测试只能写成计划，不能写成“已验证通过”。

## 调查与证据

写“现状”“复用”“对齐”前，先读取实际实现。结构性问题优先使用 codebase-memory；缺失覆盖时再读源码和 grep。

跨仓库功能至少追踪：

~~~text
用户入口
→ 前端字段
→ API / RPC / MQ
→ 服务端编排
→ 持久化
→ 下游任务或执行器
→ 回调
→ 页面状态与文件结果
~~~

跨项目契约必须写清：

- proto/API 文件、message、方法、字段和类型。
- 字段值来自哪个表、配置、前端控件或运行时来源。
- 共享 JAR、proto 子模块或生成代码如何发布和升级。
- 依赖方数量及其 bump 风险。

## 设计质量约束

- 每个新增字段都要有来源、默认值、校验、生命周期、兼容性和测试点；没有真实用途的字段不进入协议。
- 文件系统类功能优先只暴露一个逻辑根目录。叶子目录、起始文件和输出目录由执行端根据稳定 ID 和固定布局派生；若目录来自容器 volume，必须校验 mount 映射，禁止接受任意路径。
- 状态机、错误码、枚举、字段编号和表结构必须在所有模块章节中一致。
- 异步任务不能依赖 AI 或用户轮询推进；创建接口返回任务标识和管理页链接，状态由持久化和回调维护。
- 用户输入涉及 AI、前端、服务和执行器时，明确每一层谁能修改、谁只透传、谁做最终校验。
- 优先复用已有稳定能力；新增抽象前说明现有能力为何不足。
- 设计文档不重复需求背景和验收文案，只引用关联需求。
- 对旧方案、旧字段、旧状态和旧路由做全文检索，防止残留让实施者误判。

## 迭代流程

1. 重读需求和设计的当前版本。
2. 重新核对受影响代码或契约，不能只根据上一轮记忆修改。
3. 先判断变更影响哪些章节，再做局部编辑；大面积范围变化才整体重写。
4. 同步修改需求、设计中的状态、字段、范围、待决事项和最近更新。
5. 检查标题层级、代码围栏、字段编号、状态机、错误码、表和接口的一致性。
6. `rg` 搜索被删除或重命名的字段、状态、模块、路径和旧结论。
7. 报告实际修改的文件、关键结论和未解决风险；不要声称未执行的构建或测试已通过。

## 完成后检查

- 文档是否先给结论，再给证据和实现？
- 每个受影响模块是否都有“功能 / 现状 / 改造点”？
- 公共协议是否集中定义且没有多份冲突版本？
- 新增字段是否能追踪到来源、用途、校验和消费方？
- 流程、状态机、错误码和改造范围是否互相对齐？
- 需求与设计是否同步，且无关段落保持原文？
- 验收标准是否在需求文档最后？
- Markdown/Mermaid 围栏是否配平，旧名称是否已清理？
