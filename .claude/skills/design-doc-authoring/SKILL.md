# 需求/设计文档编写与迭代

## 适用场景
- 为新功能编写需求文档和设计文档
- 迭代已有文档：新增需求项、关闭待决事项、对齐现有惯例
- 用户说"写需求文档""写设计文档""更新文档""对齐X惯例""参考X的做法"时触发

## 文档存放
- 放在 `.local/_doc/{feature}/` 子目录下
- 先出需求文档，再出设计文档，实现前先文档后编码
- **模板**：新建文档时从模板起步，按实际功能增删章节（章节可裁不可凑）：
  - 需求文档：`references/requirements-template.md`
  - 设计文档：`references/design-doc-template.md`
- **元信息头**：两份文档头部均需完整的元信息块（需求编号、日期、最近更新、涉及模块、关联文档、状态、结论来源），格式见模板
- 需求文档与设计文档的"最近更新"行同步修改，说明本轮改了什么

## 跨项目/跨仓库文档组织（proto 协议下发场景）
当一个功能涉及 proto 协议变更、需多个项目协同（如 agent + apiserver + 前端 + 备份中控各仓各自消费 proto）时，文档按以下原则组织：
- **需求文档跨项目一份（共享契约）**：需求是端到端的用户行为（界面配置 → 下发 → agent 生效），拆开会漂移。写清配置字段语义、新老兼容约定（消息未下发回退默认）、各端职责边界。放在多方可见位置（团队文档系统），或至少在各仓互相引用。
- **设计文档各项目各写一份（实现细节）**：设计只对本项目开发者有意义。各仓写自己的实现细节（agent 写调度/清理实现，服务端写表单/校验/下发链路，前端写表单交互），互相之间只以 **proto 契约**为对齐锚点，不要复制对方的内部设计。
- **proto 契约是对齐锚点**：跨项目对齐靠 proto 定义本身（字段名、类型、校验规则），不靠复制对方设计文档。需求文档中"配置语义/兼容性约定"部分可抽成独立可共享版本，供各端引用。
- **字段映射章节必须列协议变更清单与上游依赖**：需求文档中"字段语义与命名映射"类章节不能只列字段名+含义+界面控件，还必须明确列出：(1) 协议在哪新增了哪些字段/消息——具体到 proto 文件名、message 名、字段名与类型（如 `backup.proto` 新增 `message SlowLogRetentionPolicy { string schedule_time = 1; ... }`）；(2) 每个字段依赖了哪些上游配置（如该字段值由 bakserver 从 `log_backup_policy` 表的哪列读取、前端表单哪个输入项映射）。这样其他模块的评审人员不用翻你仓库的代码就知道自己需要改什么、你依赖他什么。只写"前端字段名建议 camelCase"而不列协议变更源头，评审方无从判断影响范围。
- **协议变更章节保持简洁，不要拆成多个冗长子节**：用户明确反馈——逐字段语义/取值来源拆解子节（"字段语义、取值来源与上游依赖"）和"建议前后端字段命名"表（camelCase 映射）是"没意思"的，要求删除。协议变更+上游依赖合并为一个简洁章节即可；上游依赖以简短注释嵌入 proto 变更清单旁（如"schedule_time ← 前端表单 scheduleTime → log_backup_policy 表"），不展开成逐字段段落。命名是各团队实现细节，需求文档不应越俎代庖 prescribing 前后端字段名。
- **改动范围表须标注各仓库的本地可用性（以表下脚注呈现，勿做专列）**：逐个核实改动范围表里每个仓库的源码是否在本地检出，标注"本地（远端 git.midea.com/...）" vs "⚠️ 源码不在本地、仅 Maven 制品（~/.m2 缓存到 x.x.x-RELEASE）"。部分依赖库（尤其 API/JAR 制品，如 bakserver-api、provider-api）常以版本化 JAR 发布、源码仓未检出，评审方需知道哪些仓库得先找到并检出才能动手。**呈现形式用表下脚注/注释（如 `> "本地"指开发机...；datamars-bakserver-api 仅 Maven 制品`），不要在表格里加"仓库位置"专列**——用户明确要求"仓库位置这一列移除了"，专列让表过宽。不要只核实你偶然注意到的那一个——用户会让你"再检查下其他仓库"，应系统性地把表内每个仓库都核对一遍。
- **改动范围表须列出数据库表/实体类的 schema 变更**：跨项目功能新增配置字段时，配置最终要持久化到数据库表（如 bakserver 的 `log_backup_policy` 表 + `LogBackupPolicy` 实体类）。proto 变更和 API 链路变更之外，**表结构变更（新增列）是独立的改动项**，必须在改动范围表中单独列出（哪个仓库的哪个实体类/表新增了哪些列）。用户会指出"还要改动日志轮转策略表，新增字段吧"——只列 proto message 字段和 API 透传，漏掉持久层表结构变更，评审方不知道数据库也要改。调查方法：grep 实体类（如 `LogBackupPolicy.java`）的 `@TableField`/`@TableName` 注解，确认现有列与新字段是否已存在。
- 用户指明涉及的各项目路径时，需求文档需结合这些项目逐一核对配置链路（前端表单格式 → 服务端 proto → agent 消费），不要只写 agent 单仓视角。
- 调查跨项目配置链路时，对每个项目并行派发只读探索任务，追踪完整数据流（UI 表单字段 → HTTP 端点 → 控制器/服务 → RPC → gRPC 方法 → agent 步骤），标注各跳的技术栈与具体文件/方法，找出"缺口层"（需新增字段透传的中间服务层）。
- **proto 源文件常住在独立的共享库工件里，不在任一消费方仓库**：跨语言 proto 变更时，先定位 proto 源所在的共享工件——Java 侧通常发布为版本化 JAR（groupId:artifactId:version），Go 侧常为 git 子模块。各消费方通过依赖坐标（pom.xml `<artifactId>`+`<version>`、go.mod replace、子模块指针）引用。改 proto = 改源 → 重建/发布工件 → 各消费方 bump 版本或更新指针，缺一步则消费方仍用旧 proto 编译。从 Java import 包名（如 `com.xxx.agent.common.protobuf.*`）可反查所依赖的 JAR 坐标（grep pom.xml 中该 artifactId）。估算跨项目改动范围时，这一步"重建发布 + 版本 bump"不可遗漏。
- **底层共享 JAR 的依赖爆炸半径要在文档里量化**：bakserver-api / agent-lib / provider-api 这类底层 JAR 常被大量仓库依赖（一个 artifactId 可能有 10+ 个 pom 引用）。改它的 proto/接口 → 发新版 → **所有依赖方都要 bump 版本**，协调成本可能远超功能本身。用户会直接问"会不会导致大量其他仓库需要更新依赖？"。调查方法：`rg -l "<artifactId>datamars-bakserver-api</artifactId>" /项目根 --type xml` 统计依赖方清单与数量，在改动范围表下以注释列出"依赖方（需 bump 版本）"清单与 count（勿做成表格专列，用户嫌表过宽）。让评审方一眼看出协调成本，不要只写"发布新版本"一笔带过。

## 待决事项管理（用户强偏好 — 违反会引发不满）
- **已解决/已关闭的待决事项：直接删除该行并顺延重编号**，不要保留删除线 `~~已定~~` / `~~已关闭~~` 占行
- 删除后同步清理文档中对该编号的引用（如"见待决事项 #4"），或将引用改为指向设计文档具体章节
- 用户已多次强调此偏好，不要凭"留痕可追溯"的好意保留删除线

## 对齐现有惯例（用户强偏好 — 违反会被质疑）
- 设计文档中写"对齐/参考现有X惯例"前，**必须先读X的实际代码/proto逐字段核对**
- 不能凭印象断言"对齐"——用户会质疑设计是否真符合惯例
- 具体操作：grep/read 目标 proto 或 Go 代码，逐字段比对类型、校验规则（gt vs gte、范围）、命名、语义
- 例：写 proto 校验规则时，先读现有同类 message 的 `validate.rules` 写法，再照写；不要想当然用 `gte=0` 当实际惯例是 `gt=0`

## proto3 可配字段零值歧义处理
- proto3 数值字段默认零值，但零值可能是合法配置值（如 hour=0 表示 00:00、minute=0）
- 两种解法，按场景选择：
  - **消息级存在性**（对齐 binlog 保留策略惯例 `LogRetentionPolicy`/`MariaBinlogRetentionPolicy`）：配置消息整体为 nil = 未下发（回退默认），消息存在时字段值均为显式有效值（0 也合法）；用 `validate.rules` 保证范围（如 `gte=0 lte=23`）。适合纯数值字段、对齐现有同类 message 时
  - **字符串格式**：用 `string schedule_time = "HH:mm"` 替代 `int32 rotate_hour/rotate_minute`，`"00:00"` 天然合法无歧义；适合字段需对齐前端表单字符串格式（如数据备份前端 `executionTimeRange: "HH:00-HH:00"`）、或零值歧义用消息级存在性处理不够直观时
- 同一 message 内不要无理由混用两种方案（如阈值用 int + 消息级存在性、时间用 string）——除非各有对齐目标
- 用户可能对"00:00 怎么表达"有具体想法（如直接给出 `"scheduleTime": "08:00"` 格式示例），以此作为设计靶心
- 本期实践：慢日志轮转 `SlowLogRetentionPolicy` 最终用 `string schedule_time` + `string timezone`（固定偏移 `"UTC+8"`），替换原 `int32 rotate_hour/rotate_minute`——既对齐前端格式，又消除零值歧义

## 时区/时间配置字段设计（Go agent）
- 设计 proto 中的时区字段时，先排查 agent 的时区依赖：
  - `time.LoadLocation("Asia/Shanghai")` 依赖系统 tzdata 数据库；精简容器可能没有
  - 检查仓库是否 `import _ "time/tzdata"`（内嵌 tzdata，二进制增 ~450KB，但保证可用）
  - 若无内嵌且容器可能精简，优先用**固定偏移字符串**（如 `"UTC+8"`）+ `time.FixedZone` 解析，避免 tzdata 依赖
- 排查现有时间调度是否用容器本地时间（`now.Location()`）：容器若为 UTC，硬编码的"02:00"实际是北京时间 10:00——新增显式时区字段能消除此歧义，但意味着调度计算要改为按配置时区算
- **回退/默认时区应与历史行为一致**：重构既有 `time.Local` 代码时，回退路径保持 `time.Local`，不要擅自改 `FixedZone` 或 `time.UTC`；仅全新代码或确认容器 TZ 不可靠时才用 `FixedZone`。绝不 `time.UTC` 做调度时区（会偏移触发时间）。用户多次纠正此点——"保证与原有一致"优先于"显式时区更清晰"
- 时区格式（IANA 名 vs 固定偏移）决定解析方式与是否需要 tzdata——用户可能有偏好，主动询问
- **实现解析器时只支持前端实际下发的格式**——先 grep 前端代码确认提交格式（如 `rg "UTC|timezone" 前端仓库`），只实现那一种。不要投机性支持多种格式（如同时接受 `UTC+8` / `UTC-5` / `UTC+08:00`），前端只发一种就是过度设计，用户会直接指出"需要支持那么多格式吗？前端只支持一种吧"。不确定时先查代码再问用户，不要先写多格式再被发现
- 调查"参考X的开始时间"时注意：X 的时间配置可能只在前端 JSON 表单（如 `executionTimeRange: "HH:00-HH:00"`）或服务端调度层，根本不经过 agent pb——此时 agent pb 无现成类型可抄，需新设计字段

## 设计提案简洁性 — 不引入不必要的缓存/字段
- 设计文档中提议新增结构体字段或缓存时，先检查现有代码是否已用"每次现查"的方式处理同一操作
- 若现查开销可忽略（如每分钟一条轻量 SQL `SHOW VARIABLES`），**不要加缓存**——缓存引入额外复杂度（字段 + 初始化 + 失效逻辑）和过期风险（运行时配置变更后缓存不更新）
- 用户会直接质疑"为什么要新增？"——设计文档中每个新增字段都应有明确必要性说明，不能仅凭"省一次查询"就加缓存
- 实践例：慢日志轮转设计曾提议新增 `slowLogPath string` 缓存字段，但现有 `doSlowLogRotate()` 每次都是现查 `getSlowLogFilePath()`，每天一次也没问题；大小检查每分钟复用同一函数，开销可忽略 → 缓存无收益，删除

## 新功能域的结构体组织（用户强偏好）
- 为现有类型新增一个完整功能域（如 `BinlogDetectStep` 新增慢日志轮转）时，**把该域的状态与方法归入子结构体，子结构体反向引用父类型**，不要直接堆进父类型
- 父类型只保留：一个子结构体指针字段 + 初始化 + 生命周期调用（如 `go bd.slowLog.startScheduler()`）
- 目的：便于日后把该域物理拆分成独立类型/包——届时只需把反向引用换成显式依赖（配置 + 容器信息 + 生命周期接口），不用再大改父类型
- 接收者改为子结构体后去掉冗余前缀（`startSlowLogRotateScheduler`→`startScheduler`），并独立成文件（如 `slow_log_rotate.go`）
- 这是"分组"第一步：子结构体仍可直接读父类型字段，真要解耦再抽接口；不要一次性过度解耦

## "参考X的实现"调查路径
- 用户说"参考X的做法"时，**先调查X的实际实现**，不要假设X的做法
- 调查路径：读 proto 定义 → 读 Go 代码消费方 → 追踪数据流（配置从哪下发、谁触发执行）
- 参考目标可能跨仓库：参数格式/约定常先在前端或其他服务落地，当前后端仓库可能根本未携带。仅在后端找不到就断言"无先例"是错的——用户指明某仓库/路径时，优先去该处确认实际格式；调查"参数怎么传"应同时查前端表单(格式源头)、后端 proto(是否携带)、服务端调度(谁触发)
- 在前端查参数格式时，区分"查询过滤参数"（列表筛选用，如备份集查询条件）与"配置/策略表单参数"（创建/编辑策略时填写）——同名字段可能同时出现在两处但语义不同，grep 到后需读上下文判断类型，配置表单才是格式源头
- 可能发现X的做法与你假设完全不同（如：某些"开始时间"配置根本不经过 agent pb，而是服务端调度下发）
- 发现差异后主动向用户说明，给出方向选择，不要默默按假设继续
- 前端已有参数格式、但后端 proto 未携带时：用户的心智模型是"前端格式已定，只差后端怎么传"——应主动基于前端格式提出 proto 字段设计方案（类型、字段名、校验规则），而非止步于"后端无先例，你要哪种方向"。用户可能直接给出目标格式示例（如 `"scheduleTime": "08:00"`, `"timezone": "Asia/Shanghai"`），以此作为设计靶心

## 需求变更：范围缩减与剪枝已废弃可配置项（用户强偏好）
用户中途发"需求变更"把设计从**可配置改为硬编码**、并**直接复用某个平行/同类功能的现有参数**（如"阈值直接用 binlog 的阈值"）时，这通常是一次范围缩减，不只是追加一条新决策。处理要点：
1. **先定位要复用的源头**：grep 平行功能的 proto/代码确认具体字段（如 binlog 保留策略 `LogRetentionPolicy.disk_usage`），明确 agent 复用哪个已有配置/字段值，而非另立新参数。
2. **剪枝之前为"可配置"设计的整条产物**：范围缩减后，原先新增的可配置字段链路作废——proto message 字段、数据库表新列（如 `log_backup_policy` 新增列）、前端表单项、各端透传/下发链路描述都要**删除或降级**。不要只追加"改成硬编码"一句、把废弃的配置设计留在文档里造成漂移。
3. **同步收敛改动范围表与待决事项**：相关仓库的改动项随之缩水（如 bakserver 不再需要加 DB 列、前端不再需要新表单项），改动范围表同步改写；之前因"持久化方式新列 vs extra_params"等悬而未决的待决事项可能直接因硬编码而失效——删除并顺延编号。
4. **"配置下发链路"章节按新范围重写或标注**：可配置参数曾铺开的"前端→后端→中控→agent"链路，硬编码后 agent 不再从该链路取值；把链路章节中已被硬编码取代的部分删除或标注为"不再下发"。
5. grep 残留对被删字段/列名/表单项名的引用。
6. **代码侧：函数保留返回默认值、proto 移除变更（代码与 proto 区别对待）**——范围缩减后 agent 侧已写的可配置消费代码**不必完全删除**：相关函数保留结构、直接返回硬编码默认值即可，等以后需要重新开放配置时改回来即可。**注意区分仍在调用链中的函数与因改动而失去调用方的死代码函数**：前者保留返回默认值（如 `parseRotateTime`/`sizeCheckInterval`/`retainDays` 仍被调度器调用）；后者应连同其测试与因此变为 unused 的 import 一并移除（如 `parseFixedTimezone` 在时区改为硬编码本地时区后已无调用方，用户明确要求"相关也移除吧"）。留骨架的是"还在跑的函数"，不是"没人调的死函数"。但 **proto 子模块的变更应移除**（废弃 feature 分支、回退主仓 proto 改动），因为不再有消费方。操作步骤：(1) `git ls-tree HEAD proto` 取主仓记录的子模块指针；(2) 子模块 checkout 该 commit（通常是 `main` 分支指针——**不要切到 `dev`**，主仓 Go 代码依赖 `main` 分支 proto 中的新增类型如 Milvus/RabbitMQ，dev 缺这些类型，`make pb` 后编译报 `undefined: pb.EngineType_Milvus`）；(3) `make pb` 重新生成 Go pb 文件；(4) grep 清理 Go 代码中对已删 proto 消息/字段的残留引用。区别对待的理由：代码留骨架便于回退，proto 去干净避免无用字段残留与发版负担。
- 根因：用户倾向**简单 + 复用既有实现**而非新可配置项（见 USER 偏好"复用同类/平行实现""勿为对齐而提议重构，用户倾向沿用既有方案"）。"可配置 → 硬编码 + 复用 X 参数"是这一偏好的典型表现；文档若只追加新决策不剪枝旧设计，评审方会误以为还要做一堆配置链路工作。

## 按大小阈值触发的日志轮转设计（用户强偏好）
设计"日志总量超磁盘占用阈值 → 触发轮转+清理"时，**不要无条件先轮转活跃文件再清理归档**——这会在临界场景空转并产生碎片：
- 问题：归档总量贴着阈值（如归档 29% + 活跃 1% 超 30%）时，轮转只是把活跃文件 rename 成一个小归档（不释放空间），清理又只删最老一个小归档就达标，总量仍贴阈值；下次稍增即重复，归档堆满碎片小文件，还白白执行 FLUSH/轮转命令。
- 正解（最小动作原则）：**清理归档才是唯一释放空间的手段，轮转只在"活跃文件本身太大"时才必要**。设一个"最小轮转单文件大小"门槛（如 500MB），三段式判定：
  1. 总量 > 阈值 且 活跃文件 > 门槛 → 先轮转，再从旧到新删归档至达标；
  2. 总量 > 阈值 且 活跃文件 ≤ 门槛 → 只从旧到新删归档至达标，**不轮转**（复用已有的 cleanByDiskUsage，跳过活跃文件）；
  3. 兜底：归档清完仍超阈值（活跃单独已超阈值，仅小盘或存量巨型文件场景）→ 无条件轮转。
- 门槛取值：500MB 是文本日志可下载/grep 的舒适区上界，配合检查间隔（如 10min）天然限流；太小切分过频（FLUSH 多、归档碎），太大单文件难用。
- 存量特例：历史实例可能有单文件远超阈值的巨型活跃文件，必须走兜底无条件轮转，不能因"活跃未超门槛"而跳过——这是用户明确要求"还要处理存量实例单文件特别大的特例"。
- 收益：归档少而大、减少无谓轮转/FLUSH；"避免单文件过大"目标不损——每日定时轮转仍兜底切分。
- 这是用户主动指出原设计缺陷后定的方案；设计 size-triggered 轮转时默认按此三段式判定，不要回到"先轮转再清理"。需求文档 FR/验收标准与设计文档 §调度清理流程要同步落这三段式。
- **代码结构：编排入口 + 并置辅助函数（用户强偏好 — 已三次违反，极高危）**：实现三段式判定时，**不要**拆成"纯计算函数返回 plan 结构体 + 执行函数消费 plan"的 calc/exec 分离模式——用户明确否决了 `diskUsagePlan` 方案并亲自改写代码骨架。正确结构：一个编排入口函数（如 `diskUsageExceeded()`，无返回值）内联完成统计→判定→按需轮转→计算待删→执行清理全流程；辅助函数（`rotateByDiskUsage`、`cleanByDiskUsage`）并置于入口函数之后；仅当用户自己的代码骨架已提取纯计算逻辑时（如 `calcNeedRemoveFiles`），照其结构补全即可，不要自作主张再拆。**凡起"分离/提取纯函数提可测性"念头，先停下与用户确认**——用户已三次纠正此倾向。设计文档 §调度清理流程应落此"编排入口+并置辅助"结构。

## 文档迭代流程
1. 用户提出修改 → 先重读文档当前状态（避免基于旧版本编辑失败）
2. 若为实现后回写：先 read 实现代码确认最终决策（实现中可能改变设计决定，如时区从 FixedZone 改回 time.Local、字段名调整），再据实更新文档——不要凭设计时的记忆写
3. 需求文档和设计文档同步更新（改一个要检查另一个是否需要同步）
4. 改完后 grep 残留的旧表述（旧字段名、旧约定名、被替换的措辞如"每分钟"→"按配置间隔"）
5. 待决事项变更时：删除已决项 + 顺延编号 + 清理引用
6. "最近更新"行同步修改，说明本轮改了什么
7. 若"背景/现有机制"章节描述的正是本功能正在改变的机制（如"现有慢日志轮转挂在 BinlogDetectStep 上"），迭代后标注为改造前状态（如标题加"（本次改造前）"），避免读者误以为该描述是当前行为

## 常见 Pitfalls
- ❌ 保留 `~~已关闭~~` 删除线占行 → 用户会要求删除
- ❌ 凭印象写"对齐现有惯例"而未读实际代码 → 用户会质疑
- ❌ 只改需求文档忘改设计文档（或反之）→ 两份文档漂移
- ❌ 改了字段/约定名但文档其他位置仍引用旧名 → grep 检查残留
- ❌ 假设"参考X"就是照搬X的字段，实际X可能根本不在这个层面处理该问题
- ❌ 只在后端仓库找"参考X"的格式先例、找不到就断言"无先例" → 格式可能定义在前端仓库，用户会把你指过去
- ❌ 在前端 grep 到同名参数就当格式先例 → 可能是查询过滤参数(列表筛选)而非配置表单参数；需读上下文区分，配置表单才是格式源头
- ❌ 调查发现后端 proto 无先例后，只向用户报告"无先例"并问方向 → 用户其实已知前端格式，期望你基于前端格式主动设计 proto 字段
- ❌ 基于缓存的旧文档内容做编辑 → oldString 匹配失败；每次先 read 最新状态
- ❌ 设计时区字段时直接用 IANA 名（"Asia/Shanghai"）+ `time.LoadLocation` 而未确认容器有 tzdata → 运行时 LoadLocation 失败
- ❌ 实现时区解析器时投机性支持多种格式（`UTC+8` / `UTC-5` / `UTC+08:00`），而前端实际只发 `UTC+8` 一种 → 用户指出过度设计；先 grep 前端确认实际格式，只实现那一种
- ❌ 新增时区配置但未检查现有调度是否用容器本地时间（`now.Location()`）→ 遗留"容器 UTC 时硬编码时间偏移"的隐藏问题
- ❌ 调查"参考X的开始时间"只在后端 proto 找、找不到就断言"无先例" → X 的时间配置可能只在前端 JSON 表单，用户会把你指过去
- ❌ 用 int hour/minute 表达时间、0 当默认值占位 → 00:00 无法配置；改用消息级存在性或 string "HH:mm"
- ❌ 同一 message 混用"消息级存在性"和"字符串格式"两种零值解法而无各自对齐理由 → 设计不自洽，评审时被质疑
- ❌ 设计文档提议新增缓存字段而未说明必要性、未对比现有"现查"方案 → 用户质疑"为什么要新增？"
- ❌ 把新功能域的全部变量/方法直接挂到现有大结构体上 → 用户会要求拆成子结构体（便于将来物理分离），事后重构成本更高；设计阶段就应规划子结构体组织（反向引用父类型）
- ❌ 重构既有 `time.Local` 代码时，回退/默认路径改用 `FixedZone` 或 `time.UTC` → 用户要求"改回 local 时区，保证与原有一致"；回退/默认应与历史行为一致，仅全新代码或容器 TZ 不可靠时才考虑 `FixedZone`
- ❌ 实现后回写文档时只重读文档、不读实现代码 → 实现中可能改变设计决策（如时区方案从 FixedZone 改回 time.Local），文档与代码漂移；回写时先 read 实现代码确认最终决策再改文档
- ❌ 迭代文档后"背景/现有机制"章节仍以现在时描述已被本功能改变的机制 → 读者误以为是当前行为；应在标题或首句标注"（本次改造前）"等限定语
- ❌ 跨 proto 协议下发的功能只写单仓需求文档 → 各端对配置语义/兼容约定的理解漂移；需求文档应跨项目一份（共享契约），设计文档各仓各写一份（实现细节），proto 为对齐锚点
- ❌ 跨项目 proto 变更只在各消费方仓库找 proto 文件、未定位 proto 源所在的共享库工件（JAR/子模块）及其版本依赖 → 低估改动范围，漏掉"重建发布工件 + 各方 bump 版本/更新指针"这一步；Java 侧可从 import 包名反查 JAR 坐标（grep pom.xml）
- ❌ 改底层共享 JAR（bakserver-api/agent-lib/provider-api）只写"发布新版本"，未量化依赖爆炸半径 → 用户会问"会不会导致大量其他仓库需要更新依赖？"；应 `rg -l "<artifactId>X</artifactId>" --type xml` 统计依赖方 count，在改动范围表下以注释列出"需 bump 版本的依赖方"（勿做表格专列）让评审方看到协调成本
- ❌ 跨项目需求文档的"字段映射"章节只列字段名+含义+界面控件，不列协议变更清单（哪些 proto 文件新增了哪些 message/字段）和上游依赖（各字段值从哪个上游表/配置读取）→ 其他模块评审人员无从判断自己需改什么、你依赖他什么；必须文件级枚举 proto 变更 + 标注上游配置依赖
- ❌ 在协议变更清单旁另设"建议前后端字段命名"表（camelCase 映射）和逐字段语义/取值来源拆解子节 → 用户认为"没意思"要求删除；命名是各团队实现细节，需求文档不应越俎代庖；协议变更+上游依赖合并为一个简洁章节，上游依赖以简短注释嵌入即可
- ❌ 多项目改动范围表只列项目/改动/状态、未标注各仓库是否本地检出 → 评审方不知道哪些 API/JAR 仓库（源码不在本地、仅 Maven 制品）得先找到并检出才能动手；且只核实了偶然注意到的一个仓库就收手，用户会要求"再检查下其他仓库"。应在表下脚注逐个核实标注，**不要加"仓库位置"表格专列**（用户要求移除该列，嫌表过宽）
- ❌ 跨项目改动范围表只列 proto message 字段变更和 API 透传链路、漏掉数据库表/实体类的 schema 变更（新增列）→ 用户会指出"还要改表加字段"；配置持久化层的表结构变更（哪个实体类/表新增哪些列）是独立改动项，必须单独列出；调查时 grep 实体类的 `@TableField`/`@TableName` 注解确认现有列
- ❌ 用户发"需求变更：不需要参数可配置，基于硬编码来做，阈值直接用 X 的阈值"时，只追加"改为硬编码"一句、保留原先为可配置设计的 proto 字段/DB 新列/前端表单/下发链路 → 文档与缩减后的范围漂移，评审方误以为还要做配置链路；应 grep 定位要复用的 X 字段，剪枝整条作废的可配置产物，并同步收敛改动范围表与待决事项
- ❌ 范围缩减后把 agent 侧已写的可配置消费代码完全删除 → 用户要求"相关函数直接返回默认值即可，不必完全删除，等以后需要开放配置时改回来"；保留函数骨架（返回硬编码默认值）便于将来回退。但 **proto 变更应移除**（废弃 feature 分支 / 回退主仓 proto 改动），代码与 proto 区别对待——代码留骨架，proto 去干净
- ❌ 大范围需求变更（如整条可配置链路作废）仍逐处 edit 修补旧文档 → 对抗已失效内容，oldString 易匹配失败且留残片；变更波及大半文档时直接用 write 整体重写，再 grep 残留旧字段/旧约定引用
- ❌ 回退/移除 proto 子模块变更时直接 `git checkout dev` → 主仓 Go 代码依赖 `main` 分支 proto 中的新增类型（Milvus/RabbitMQ 等），dev 缺这些类型，`make pb` 后编译报 `undefined: pb.EngineType_Milvus`；应 `git ls-tree HEAD proto` 取主仓记录的子模块指针再 checkout 该 commit（通常在 `main` 上），而非随意切到 dev
- ❌ 按"总量超阈值 → 先轮转活跃文件再清理归档"无条件执行 → 临界场景空转、归档碎片化（小归档反复生成又删除）；应设最小轮转单文件门槛（如 500MB），活跃文件未超门槛时只清归档不轮转，归档清完仍超阈值才兜底无条件轮转（覆盖存量巨型单文件特例）
- ❌ 把大小触发轮转拆成"纯计算函数返回 plan 结构体 + 执行函数消费 plan"的 calc/exec 分离 → 用户明确否决 `diskUsagePlan` 方案，要求编排入口函数（无返回值）内联完成全流程 + 辅助函数并置其后；凡起"分离/提取纯函数提可测性"念头先停下确认（已三次违反，极高危）
- ❌ 文档同步完成后声称"代码已验证通过"但未实际运行构建命令 → 用户检查发现语法错误；文档迭代后必须重新 `go build`/`go test`（或项目等效命令）确认代码可编译，不要凭早期验证结果或印象断言
