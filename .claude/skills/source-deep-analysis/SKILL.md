# 源码深度分析（source-deep-analysis）

对目标代码库做证据驱动的源码分析。核心纪律：**每个判断必须落到可定位的源码证据
（`file:line`），严格区分「源码事实」与「合理推测」**。方法论源自 xiaonancs/codex-source-analysis
的七阶段工作流与七维分析框架，并适配本环境（codegraph、子 agent 并行）。

**学习源码的第一目标是还原设计**：它遇到了什么问题（踩过什么坑）或要满足什么需求，
才需要这个设计；其次是它怎么跨过这个坑（解决思路，含取舍与代价）；最后才是实现细节。
实现细节服务于前两者，不能反过来主导叙事。

## 第 0 步：规模判定（决定流程深浅）

先确认分析对象与范围，再按下表选档。拿不准时问用户一句话。

| 档位       | 典型触发                                          | 流程                                               |
| ---------- | ------------------------------------------------- | -------------------------------------------------- |
| **功能级** | "XX 功能是怎么实现的"（如：apply_patch 如何工作） | Phase 1 → 4，只写一份功能深潜报告                  |
| **模块级** | "分析 XX 模块/子系统"（如：沙箱体系、工具系统）   | Phase 1 → 4，报告含模块内多子系统拆解 + 1 张全景图 |
| **项目级** | "分析整个项目/仓库"、"学习它的设计"               | 全 6 阶段，产出总纲 + 多章 + 附录                  |

无论哪档，最后都要问用户产出放哪（默认在当前目录建 `analysis-<项目名>/`）。

**非交互模式**（测试/CI/子 agent）：凡"给用户过目/确认"的交互点，改为把产物写出、
标注"默认值已采用"后继续执行，不得卡死等待确认；最终报告仍按正常格式交付。

## 学习目标与叙事顺序（问题优先）

读源码是为了学设计，不是为了抄实现。每个分析单元按下面的顺序展开，**顺序本身就是纪律**：

**第一步·问题与需求（为什么需要它）**：先还原"当时遇到了什么"，两类分开写——
- **坑驱动**：故障、性能瓶颈、一致性/并发问题、容量与成本压力、兼容性事故；
- **需求驱动**：新功能、新场景、新硬件/新协议、上层模块提出的约束。

找证据的入口（按可靠性排序）：① 直接证据——注释里的 `TODO/FIXME/NOTICE/Attention/XXX`、
错误码与重试/超时/限流分支、防御性代码与不变量断言、版本兼容分支（如 `DATA_VERSION_*`）、
配置开关与阈值、缓存/池化/批量的痕迹、测试用例名（`test_*timeout/retry/limit/boundary`）、
commit message / PR / issue；② 间接证据——竞品为什么不这么做、文档或论文描述的同类难题；
③ 结构证据——某个设计只有"为了绕开 X"才解释得通时，反推问题是什么。

**第二步·解决思路（怎么跨过去）**：写清总体思路、关键取舍（为什么选 A 不选 B）、
代价与新引入的约束。方案必须能对回代码落点，不能停留在"它做了归并/加缓存"这种复述。

**第三步及以后才是本质定位与实现细节**：实现细节不允许先于问题与方案出现。

**无直接证据时的纪律**：动机类判断拿不到源码/git/issue 证据时，统一写成
"可能/或许/不排除"，并给出推断依据（结构反推、竞品对照、常理）；禁止替作者编故事，
也禁止把"我认为合理"写成"它为了解决 X"。

**必产出：问题-对策对照表**（每个分析单元一张，缺表即为不合格）：

| 问题/需求 | 证据（`file:line` / commit / issue） | 对策（解决思路） | 代码落点 | 代价/遗留 |
| --- | --- | --- | --- | --- |

## 问题规划（读码前先定问题清单，给用户过目）

任何"XX 怎么实现"类问题都由四要素构成：**问题**（它遇到了什么坑/要满足什么需求，
为什么需要这个设计）、**宿主**（它在什么体系/框架里存在）、**机制**（它自己怎么运作）、
**协作**（它和哪些模块交换什么、对方为何存在）。"问题"要素必须先于其他三要素给出，
且要么带证据线索、要么明确标为待验证，不能先写成结论。功能级/模块级分析在读码前必须先
判断问题类型，按模板实例化出具体问题清单，给用户过目后再执行；清单允许增删，但需说明理由。

| 问题类型                                            | 实例化后的问题集                                                                                                       |
| --------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **可插拔成员**（类型/工具/handler/feature flag 等） | ① 现有体系什么样 ② 如何新增一个同类成员（扩展点、必实现协议、注册位置）③ 目标成员如何在该框架下实现 ④ 对接模块及其作用 |
| **算法/流程**                                       | ① 输入输出与所处阶段 ② 核心算法/状态机逐步拆解 ③ 不变量、边界与失败路径 ④ 性能特征与涉及的协作模块                     |
| **协议/数据流**                                     | ① 端到端数据流图 ② 各环节格式与编码 ③ 失败/重试/一致性处理 ④ 收发双方各自如何消费                                      |

确认后的问题清单直接映射为报告章节顺序，按七维框架各维展开；
类体系骨架、通用端到端路径、特化注入点作为④实现细节的分析方法承载（见下）。

## 七维分析框架（每章/每个分析单元的骨架，按"先问题后方案再细节"排序）

1. **问题与需求（Why）**：它遇到了什么坑/要满足什么需求，为什么需要这个设计。必须落到
   证据（注释、防御性分支、错误码、版本兼容分支、测试、commit/PR/issue）；无直接证据的
   动机按"推断"标注并给出依据（见「学习目标与叙事顺序」）。先写这一维，再写后面六维。
2. **解决思路（How）**：跨过这个坑的总体思路（架构设计、核心结构、关键算法/协议），
   以及关键取舍（为什么选这条路、备选为什么不行）、代价与新引入的约束。
3. **本质与定位（Where/What）**：该机制在架构中的定位是什么（用 trait/接口实现、持有关系、
   调用面证明）。放在问题与方案之后写——先让读者知道"为什么有它"，再知道"它是谁"。
4. **实现细节**：关键路径 / 函数 / 数据流，附 `file:line` 引用与代码片段。按三段方法展开：
   - **类体系骨架**：先交代功能依附的父类/接口、兄弟实现、基类读写协议与挂载点
     （如 `Field` 基类的 store/val_xx 虚函数协议 → `Field_str` → `Field_longstr` →
     `Field_blob`，兄弟有 `Field_varstring` 等），回答"这个项目里一个 XX 是怎么实现的"；
   - **以通用端到端路径为主干**：不含本功能特化的标准数据流/调用链，从入口 API 到
     最终存储或返回，带 `file:line`（如 INSERT 通用链：mysql_insert → ha_write_row →
     引擎行转换）；
   - **特化注入点标注其上**：在通用路径每个环节标注"本功能哪里不一样"
     （如 store 写指针不写数据 / write_row 后追加溢出处理 / 读取需回表），
     让读者看到"机器怎么转、本功能在哪改变走向"，避免"懂了每个零件、不知道机器怎么转"。
5. **易错点**：陷阱、边界条件、隐式依赖——与第 1 维呼应：这些坑在实现里如何被规避、
   哪些边界仍会复现。
6. **竞品/同类对比**（可选，功能级可省）：同类项目遇到过同样的问题吗？怎么解的？差异在哪？
7. **仍存缺陷**：哪些问题没有被真正解决、这个方案引入了什么新的代价（不藏拙）。

## 各阶段流程

### Phase 1 源码通读与量化

- 仓库未拉取时先 clone 到临时目录（`--depth 1`，除非需要历史）。
- 建立规模快照：目录树、语言构成、LOC 排名（`find ... | xargs wc -l` 或 cloc）、
  模块/crate/package 清单。大仓库先列出 TOP 10 最大的子系统。
- 建立骨架：功能级→一个分析单元；模块级→2-5 个单元；项目级→8-25 章的
  `chapters.yaml`（含 id/title/关键源码路径），先给用户过目再往下走。
- **先做"问题考古"再通读实现**：按「学习目标与叙事顺序」的证据入口，先产出该分析单元的
  问题清单（每条带证据线索或标注待验证），再进入实现通读。
- **功能级先完成问题规划（四要素 + 问题类型实例化）再进入通读**，规划确认后
  问题清单与骨架合并给用户过目。
- **接入 codegraph（强制，先于任何 rg/grep 检索）**：
  1. 先 `codegraph status <path>` 确认索引：无索引则 `codegraph init` + `codegraph index`，
     有索引但源码有变更则 `codegraph sync`。**禁止未检查就断言"本环境无 codegraph"**。
  2. 符号定义、调用者、被调用者、调用链检索一律用 codegraph
     （`query`/`callers`/`callees`/`explore`/`node`），把调用图作为骨架的证据基础。
  3. rg/grep 仅用于字面文本（注释、宏、字符串、错误消息）或 codegraph 覆盖不到的
     场景，且在核验记录中注明哪些结论只能靠文本检索。
  4. **未命中回退**：复合符号（C++ 限定名、重载）在 `node`/`callers` 查不到时，
     先用 `query` 搜短名或 `explore` 搜区域，仍不行才回退 rg 字面定位，
     并在核验记录中注明该处回退原因。
  5. **输出量控制**：大仓库 `explore` 用 `-n`（max-nodes）限流或管道 `head` 截断，
     防止单次数百符号的关联噪声挤占上下文。
  6. **已知误报**：codegraph 输出的 "different git worktree" 警告在目标仓库
     已由 `status` 确认 up-to-date 时可忽略（相对 cwd 的误报），以 `status` 结果为准，
     勿被误导去做多余 init/sync。

### Phase 2 外部认知基线（仅项目级，模块级可选）

- 双轨调研：官方一手（官方文档、博客、issue/PR）+ 第三方分析（技术博客、社区讨论）。
- 产出三清单：**社区共识**（低争议事实）、**主要分歧与误解**、**社区盲区**
  （高复杂度低讨论区）——盲区即后续章节重点补齐对象。
- 调研内容只是入口，结论必须回到源码验证；二手叙事与源码冲突时以源码为准。

### Phase 3 分单元生成（七维框架）

- **接入子 agent**：模块级/项目级用 Task 工具并行派发多个分析子任务，每个子任务
  负责一个分析单元，prompt 中必须包含：已确认的问题清单（该单元对应哪几问）、
  读者设定（按不熟悉本项目源码的工程师对待）、**问题优先的七维顺序（问题与需求 →
  解决思路 → 本质定位 → 实现细节 → 易错点 → 对比 → 缺陷）与"问题-对策对照表"要求**、
  七维框架（④实现细节的三段分析方法）、
  `file:line` 引用纪律、定量快照要求、输出格式、**codegraph 检索纪律（先 status/sync，
  符号与调用链用 codegraph，rg 仅作字面文本补充；告知索引状态与项目路径）**。
- 串行依赖的单元（如先总后分、骨架先于特化单元）按依赖顺序派发，勿盲目并行；
  首个单元产出的类体系骨架/通用端到端路径结论可下发给后续子任务复用。

### Phase 4 核验（不可跳过，过程留痕但不进报告）

核验是**给 agent 自己做的过程纪律**，交付报告面向读者，**不得出现"核验说明"之类的
元章节**。核验留痕写在报告之外的独立文件（如 `verification.md`，随工作区留存但不作为
交付物），内容包括：实际采用的核验手段、codegraph 未命中/文本检索回退点、
抽查清单与结果。

- **codegraph 核验调用链**：报告中画出的每条调用链路，用 codegraph
  （`callers`/`callees`/`node`）核对是否真实存在，函数名/文件路径是否准确。
- **codegraph 确实不可用时**（已用 `codegraph status` 检查而非凭印象）：读调用点
  上下文行（如 `sed -n 'A,Bp' file`）确认调用方向与顺序真实存在。**grep 只能证明
  符号存在，不能作为调用关系的证据**。
- 抽样核验 `file:line` 引用：随机抽 ≥5 处，重读源码确认行号与内容一致，
  结果记入核验记录（不能只凭"写报告时查过"的自我声明）。
- **问题-对策对照核验**：报告里每条"问题/需求"都要能追到证据（`file:line`/commit/issue）
  或明确标注为推断；每条"对策"都要在代码里有落点，落点对不上就改结论。
- 区分措辞：源码可证的用陈述句；动机推断统一用"可能 / 或许 / 不排除"。
- 每个分析单元末尾附**定量快照**：关键文件实测行数、核心函数行数、test 数量等
  （脚本统计，不凭印象）；功能级报告只有一个单元时，集中放在报告末尾统一一节。

### Phase 5 汇总与整理

- 项目级：写总纲（项目坐标 / 设计哲学 ≥6 条 / 整体架构图 / 一次典型请求的数据流 /
  关键子系统盘点 / 火爆原因或优劣分析 / 设计权衡）+ 各章 + 附录
  （B：关键 struct/class/函数 速查表；C：参考文献）。
- **多文档产出必须附阅读指南**（项目级总纲+章节+附录，或模块级被拆成多篇时），
  作为读者进入正文的第一个文件（或总纲第一节）：
  - 按推荐阅读顺序逐项列出"先读 X，了解 Y；再读 A，了解 B"——每份文档说明它回答
    什么问题、读完能获得什么；
  - 给出典型读者路径（如：只关心某功能 → 读总纲 + 第 N 章；想全面理解 → 按顺序通读）；
  - 标注章节间前置依赖：哪些章依赖前面结论、哪些可跳读/并行读；
  - 阅读指南本身不承载分析内容，只做导航，保持一页以内。
- 模块级：报告 = 全景图 + 各分析单元（每个单元含"问题-对策对照表"）+ 速查表。
- 功能级：单篇报告按七维框架直接成文。
- 无论哪档，报告开头（总纲或引言）先给"它遇到了什么问题 → 怎么解决"的摘要，再进入
  定位与实现细节；阅读指南的第一条要说明这份分析回答的是哪个设计问题。

### Phase 6 图表校验与交付

- Mermaid 图（架构/流程/时序）逐块语法校验（`mermaid-cli` 或 `npm i mermaid` +
  解析脚本），不过校验的图必须修。
- 文风统一：判断句有证据、推测有标记、量化有出处。

## 输出格式约定

### 调用链与机制分析（遵循 code-analyze skill）

涉及调用链梳理、模块协作、流程与注入点分析时，先加载 `code-analyze` skill，按其约定输出：

- 输出目标固定为：关键调用链、模块职责划分、数据结构/trait/接口关系、扩展点/注入点、
  关键控制流与状态变化
- 回答风格：先给结论，再给调用链和证据；解释复杂调用用"谁调用谁"，优先回答
  "为什么会调用到这里"而不是只回答"在哪里定义"
- 宏/derive 生成代码须区分手写实现、宏展开隐含实现、运行时真实调用方向；
  visitor/planner/builder 模式须说明遍历入口、注入点、状态存放、可否中断
- 非直接源码证据的结论标注"推断"（与本 skill 的事实/推测措辞纪律一致）

### 图示规则

- 调用链图、模块协作图：优先 fenced `text` 代码块文本图（总图 / 调用链 / 模块协作
  三种模板见 code-analyze skill），不强行 Mermaid 化
- 架构图、数据流图、状态图：用 Mermaid，逐块语法校验（`mermaid-cli` 或
  `npm i mermaid` + 解析脚本），不过校验的图必须修。
  mermaid-cli（mmdc）依赖 puppeteer/Chromium，受限环境装不上时用 jsdom + `mermaid.parse`：

  ````js
  // scripts/check-mermaid.mjs  用法: node check-mermaid.mjs report.md
  const fs = require("fs");
  const { JSDOM } = require("jsdom");
  global.window = new JSDOM("").window;
  global.navigator = global.window.navigator;
  (async () => {
    const mermaid = (await import("mermaid")).default;
    const src = fs.readFileSync(process.argv[2], "utf8");
    const blocks = [...src.matchAll(/```mermaid\n([\s\S]*?)```/g)].map(
      (m) => m[1],
    );
    for (const [i, b] of blocks.entries()) {
      try {
        await mermaid.parse(b);
        console.log(`block ${i + 1}: OK`);
      } catch (e) {
        console.error(`block ${i + 1}: FAIL\n${e.message}`);
        process.exitCode = 1;
      }
    }
  })();
  ````

- 功能级报告至少 1 张**端到端流程图**：通用路径为主干，特化注入点在图上标注
  （对应④实现细节的特化注入点标注），让读者看到"机器怎么转、本功能在哪改变走向"

### 引用与基线

- 每个 `file:line` 引用格式：`` `path/to/file.rs:123` ``，代码片段前注明来源行号
- 结论先行/摘要中的 `file:line` 必须是**支撑该结论的最直接证据**（函数体/关键分支），
  不能是外围宏、注释或次要定义——读者点开引用应能直接看到结论依据
- 章节内小节按七维框架顺序展开：问题与需求 → 解决思路 → 本质定位 → 实现细节
  （以通用端到端路径为主干、注入点标注其上）→ 易错点 → 对比 → 缺陷；
  全网调研补充（若有）放在问题与需求之后、解决思路之前，用于判断"这是行业共性难题
  还是本项目特有的坑"
- 报告开头给"源码基线"段：commit/版本、仓库 URL、拉取日期、规模统计，保证可复现
- 面向读者的行文与详略按"不熟悉本项目源码的工程师"设定（前置概念
  与关键细节不可省略），但无需在报告中写"读者身份声明"之类的元说明
